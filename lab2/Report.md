Освоить принципы написания эффективных и безопасных Dockerfile-манифестов, научиться выявлять и исправлять распространенные антипаттерны, а также понять важность правильной эксплуатации контейнеров.

- Написать “плохой” `Dockerfile`, в котором есть не менее трех “bad practices” по написанию докерфайлов
- Написать “хороший” `Dockerfile`, в котором эти плохие практики исправлены
- В `Readme` описать каждую из плохих практик в плохом докерфайле, почему она плохая и как в хорошем она была исправлена, как исправление повлияло на результат
- В `Readme` описать 2 плохих практики по работе с контейнерами.

Теперь разберем в чем заключаются плохие практики написания `dockerfile`.  

- **Непредсказуемый базовый образ**  
  В bad.Dockerfile использован ubuntu:latest. При сборке подтянулась последняя версия Ubuntu с Python 3.12, где теперь нельзя просто так ставить пакеты через pip в системный Python (PEP 668).
  
  **Влияние:** Сборка ломается, зависимости не устанавливаются.
  
  **Исправление:** В хорошем Dockerfile используем python:3.11-slim — фиксированная версия Python, все зависимости ставятся предсказуемо.
  
- **Установка пакетов Python глобально**  
  В bad.Dockerfile pip ставит зависимости сразу в систему без виртуального окружения.
  
  **Влияние:** Среда не изолирована, приложения могут ломаться при обновлениях или конфликтах версий.
  
  **Исправление:** В плохом Dockerfile создали виртуальное окружение, а в хорошем используем официальный Python-образ, где все уже изолировано.

- **Копирование только нужных файлов vs `COPY . /app/`**  
  В плохом Dockerfile использовалась команда `COPY . /app/`, которая копирует в контейнер все файлы из текущей директории, включая `.git`, локальные конфигурации, временные файлы и другие ненужные данные.  

  **Влияние:**  
  - Образ становится больше из-за лишних файлов.  
  - Потенциально увеличивается время сборки, так как Docker проверяет хэш всех файлов для кэширования слоёв.  
  - Могут попасть приватные или временные файлы, что создаёт риски безопасности и мешает воспроизводимости.  

  **Исправление:**  
  В хорошем Dockerfile используются точечные команды `COPY requirements.txt /app/` и `COPY app.py /app/`. Это позволяет:  
  - Копировать только необходимые файлы для работы приложения.  
  - Эффективнее использовать кэш слоёв при пересборке, так как изменения в других файлах не ломают кэш установки зависимостей.  
  - Делать образ компактнее и безопаснее.  

- **Раздельные RUN для apt-get update и install**  
  В bad.Dockerfile сначала apt-get update, потом отдельный RUN для apt-get install.
  
  **Влияние:** Кэширование работает хуже, образ становится больше.
  
  **Исправление:** Команды объединены в одну строку, добавлен флаг --no-cache-dir для pip, образ стал компактнее.

- **Использование `--no-cache-dir` при установке Python-зависимостей**  
  В плохом Dockerfile зависимости устанавливались обычным `pip install -r requirements.txt` без параметров.  

  **Влияние:**  
  - Pip кэширует установленные пакеты внутри слоя Docker-образа, что увеличивает размер образа.  
  - Кэш может оставлять временные файлы и артефакты, которые не нужны для работы приложения.  

  **Исправление:**  
  В хорошем Dockerfile используется команда `pip install --no-cache-dir -r requirements.txt`. Это позволяет:  
  - Устанавливать зависимости без создания кэша внутри образа.  
  - Сделать образ компактнее и чище.  
  - Сократить время и ресурсы, необходимые для загрузки и хранения лишних файлов.
  
- **Плохой порядок инструкций (Incremental build time)**    
  В плохом Dockerfile сначала копировался весь проект (`COPY . /app/`), а потом устанавливались зависимости, из-за чего при изменении любого файла весь образ пересобирался заново. Согласно статье Tibor Vass, порядок инструкций имеет значение: шаги нужно располагать от наименее часто изменяющихся к наиболее часто изменяющимся, чтобы кэш использовался эффективно. В исправленном Dockerfile сначала копируется только `requirements.txt` и устанавливаются зависимости, а потом копируется исходный код, что ускоряет пересборку при изменениях кода.  

  ### Плохие практики работы с контейнерами

Во время работы с Docker я столкнулся с несколькими ошибками, которые являются распространёнными плохими практиками при эксплуатации контейнеров:

- **Конфликты портов у разных контейнеров**  
  В процессе экспериментов я запускал несколько контейнеров одновременно, и если два контейнера пытались использовать один и тот же порт на хосте (например, 8000), то запуск нового контейнера заканчивался ошибкой. Docker выдавал сообщение о конфликте:  
Conflict. The container name "/bad-app" is already in use...

Это классическая проблема: при работе с несколькими контейнерами нужно следить, чтобы порты не пересекались, либо использовать разные порты на хосте через `-p HOST_PORT:CONTAINER_PORT`. В лабораторной работе я столкнулся с этим при запуске плохого контейнера, а потом пришлось удалять старый контейнер, чтобы освободить порт.

- **Забывание остановки неиспользуемых контейнеров**  
После тестирования плохого образа контейнер `bad-app` продолжал числиться в системе, хотя я больше не использовал его. Это приводило к лишнему расходу ресурсов (CPU, RAM) и создаёт путаницу при дальнейшей работе. В реальной работе важно останавливать и удалять контейнеры, которые больше не нужны:  
```bash
sudo docker stop bad-app
sudo docker rm bad-app
```

## Вывод
В ходе лабораторной работы я изучил принципы написания Dockerfile и освоил основные отличия между «плохими» и «хорошими» практиками при создании Docker-образов.  

На практике было выявлено несколько ключевых моментов:  

1. **Выбор базового образа критически важен.** Использование непредсказуемого образа вроде `ubuntu:latest` может привести к неожиданным проблемам с зависимостями и несовместимостью версий. Фиксированные образы, например `python:3.11-slim`, позволяют создавать предсказуемые и стабильные окружения.  

2. **Правильная структура Dockerfile ускоряет сборку и уменьшает размер образа.** Объединение команд установки пакетов, создание виртуального окружения и правильный порядок инструкций позволяют эффективно использовать кэш и сокращают время пересборки при изменении кода.  

3. **Контейнеры требуют внимательной эксплуатации.** Конфликты портов и забытые работающие контейнеры могут создавать лишние ошибки и потребление ресурсов. Регулярная проверка, остановка и удаление неиспользуемых контейнеров — обязательная практика при разработке и тестировании.  

В целом, работа показала, что соблюдение «хороших» практик Dockerfile и аккуратное управление контейнерами не только упрощает разработку, но и делает процесс более предсказуемым, безопасным и удобным для масштабирования и дальнейшего сопровождения.
